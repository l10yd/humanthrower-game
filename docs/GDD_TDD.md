# HUMANTHROWER — Game Design Document + Technical Design Specification

**Версия:** 1.0 (production-ready baseline) · **Статус:** approved for First Playable
**Рабочее название:** HUMAN THROWER · **Жанр:** physics-based arcade / ragdoll puzzle / falling-body survival / row-clearing
**Платформа:** браузер (desktop / laptop / tablet / mobile) · **Сессия:** 2–6 минут, мгновенный рестарт
**Технологический стек:** TypeScript + Vite + PixiJS v8 + Rapier 2D + Web Audio API + Playwright

> Философия проекта:
> **“You don't control the falling humans. You control the human who survives underneath them.”**
> “Physics creates the situation. The grid gives the situation rules.”
> “The chaos should come from bodies interacting, not from random impulses.”
> “Every cleared row should create a new interesting physical situation.”

---

## 1. Executive Summary

**HUMAN THROWER** — браузерная 2D-игра с премиальным stylized-видом, в которой игрок управляет **одним человечком на дне вертикального стеклянного стакана**. Сверху в стакан с нарастающей частотой падают ragdoll-люди шести архетипов (NORMAL / SMALL / TALL / FAT / LIGHT / HEAVY). Игрок не катапультирует никого — он **сам активный персонаж**: бегает, прыгает, уворачивается, stomp-ит прыжком по куче, проталкивает тела вниз и помогает стакану не переполниться.

Под физикой живёт **логическая Tetris-сетка (9 × 13)**. Она не превращает ragdoll в ровные блоки — она **нормализованно замеряет занятость ячеек** ориентированными probe-весами и решает, когда строка заполнена. Заполненная строка проходит фазы **Warning → Dangerous → Clear → Recomposition**, после чего уничтожается **только то, что реально попало в строку**: человечек, чей torso попал в строку, а head и legs остались выше/ниже, **разделяется на независимые stackable pieces** — это главная фишка игры (Detachment System).

**Ключевые факты:**

| Параметр | Значение |
| --- | --- |
| Жанровая формула | ragdoll physics × falling-body survival × row-clearing × платформенный контроллер |
| Разрешение (logical) | 720 × 1280, фиксированный gameplay aspect, letterbox-масштабирование |
| Стакан | 9 колонок × 13 видимых рядов, ячейка 68 px, spawn-зона сверху, danger line на ~82% высоты |
| Физика | Rapier 2D, fixed timestep 60 Hz + accumulator, максимум 3 substeps, жёсткие velocity caps |
| Скелет NPC | 3 core-модуля (head / torso / legs) + 4 limb-сегмента, 6 revolute joints с angular limits |
| Управление игроком | hybrid character controller (не raw physics): acceleration / coyote / jump buffer / air control / stomp |
| Main tech risk | ragdoll-стабильность в переполненном контейнере → решается политикой сна, LOD и caps (§8, §30) |
| Критерий fun | прототип весел **до** добавления контента: одна механика (выживание + row clear + detach) уже играбельна (§57) |

**Scope:** MVP = 6 архетипов, полная игровая петля, score/combo, responsive UI, звук, сейв лучшего счёта. Post-MVP = новые архетипы, модификаторы среды, челленджи, косметика, leaderboard-ready архитектура. Multiplayer не планируется.

## 2. Game Pillars

Каждый пилон — это правило дизайна + способ его измерить (QA-гейт).

### P1 — “You control the survivor”
Игрок управляет только выжившим человечком. Падающие люди — это **среда и угроза**, а не снаряды игрока.
- *В дизайне:* нет катапульт, нет бросков, нет прицеливания; всё влияние на мир — через движение, прыжок и stomp.
- *Гейт:* в коде не существует механики запуска тел игроком; игрок может только перемещаться/прыгать/stomp-ить.

### P2 — “Physics creates the situation, the grid gives it situation rules”
Физика честно расставляет тела — криво, живо, комично. Сетка **не искажает физику**, она лишь **замеряет** её и выносит вердикт: строка заполнена / уничтожить эти модули / эти части остаются.
- *В дизайне:* после clear не бывает «телепорта» тел и классического сдвига рядов; пустоты сохраняются, тело физически падает в освободившееся место.
- *Гейт:* grid-слой не имеет API для перемещения rigid body; единственный обратный канал — destroy / detach / wake (§41).

### P3 — “Chaos should be readable”
Хаоса много, но игрок всегда понимает: почему тело упало туда, почему перевернулось, почему ряд исчез, почему часть осталась.
- *В дизайне:* readable silhouettes, подсветка заполненных рядов, warning-фаза, детерминированные fallback-паттерны спавна, никакого «рандомного взрыва».
- *Гейт:* QA-сценарии воспроизводимы по seed; любой game over объясним из логов grid/physics (§52, §54).

### P4 — “Heavy but soft, never explosive”
После приземления тело **не взлетает, не отпружинивает и не улетает в космос**. Никаких случайных катапультирований — ни от физики, ни от clear.
- *В дизайне:* low restitution, высокий friction, damping, velocity/impulse caps, sleeping, controlled stabilization.
- *Гейт:* автотест «ни одно тело не превышает velocity cap ни в одном из 9 сценариев» (§31).

### P5 — “Every clear creates a new situation”
Каждый row clear — это не «минус строка», а **новая физическая головоломка**: появившиеся independent pieces, новые пустоты, новые возможности для stomp.
- *В дизайне:* detachment — центральная фишка; pieces остаются в игре и заполняют будущие ряды.
- *Гейт:* после 10+ подряд clear'ов игра остаётся играбельной, стакан не деградирует в нечитаемый мусор (§31).

## 3. Core Loop

### 3.1 Макро-цикл (вся сессия)

```text
MENU → PLAYING ⟲ [ Spawn → Fall → Collide → Ragdoll → Settle → Accumulate
                    → Row Filled → Warning → Dangerous → Clear → Recompose ] → GAME OVER → RETRY
```

- **Spawn:** Spawn Director выбирает x-коридор (с учётом player, stack, anti-frustration) и архетип (по difficulty-весам), активирует подготовленный из пула ragdoll.
- **Fall → Collide → Ragdoll:** тело падает с archetype-зависимым air drag, сталкивается с кучей, болтается конечностями, переворачивается.
- **Settle:** энергия гасится (landing damping → settling → sleep). Тело остаётся физическим объектом, но почти не двигается.
- **Accumulate:** grid-слой каждые 3 physics-шага (20 Гц) замеряет занятость ячеек.
- **Row Filled → Warning → Dangerous:** строка заполнилась (порог 8/9 ячеек) → 0.45 s warning (подсветка + звук) → 0.7 s «опасная фаза», где игрок может перепрыгнуть/уйти/stomp-ить.
- **Clear → Recompose:** транзакция уничтожает попавшие в строку модули, разрывает joints осиротевших человечков, превращая выжившие части в independent pieces; физика честно перестраивает стакан; grid пересчитывается; цепочка может запустить следующий clear (multi-row bonus).

### 3.2 Микро-цикл игрока (каждые 2–5 секунд)

```text
прочитать стек → выбрать позицию → увернуться от падающего → прыжок → (dive) stomp по куче
→ занять безопасный карман → встретить следующий spawn
```

### 3.3 Тайминги типичной петли (стартовые значения)

| Событие | Период / длительность |
| --- | --- |
| Spawn interval | 2.7 s (D1) → 0.9 s (D7), floor 0.8 s |
| Падение тела с верха стакана | ~0.9–1.1 s |
| Стабилизация тела после приземления | 0.6–1.2 s до sleep |
| Полный цикл row clear | ~1.45 s (warning 0.45 + danger 0.7 + clear 0.15 + recompose 0.15) |
| Grid-сэмпл | каждые 3 physics-шага (20 Гц) |
| Уровень сложности | +1 каждые 40 s выживания, cap D7 |

## 5. Player Design

### 5.1 Тело

- **Один rigid body** (вертикальная капсула), `fixedRotation` — игрок не кувыркается, предсказуем.
- Размер: 50 × 72 px (≈ 0.74 × 1.06 ячейки) — меньше NORMAL-человека, «шустрик».
- Масса: 62 (сопоставима с NORMAL torso+head, чтобы тяжёлые тела толкали игрока, но лёгкие — нет).
- Коллизии: player × HUMAN_CORE / PIECE / CONTAINER / FLOOR — solids; player × HUMAN_LIMB — мягкие (лёгкие конечности почти не влияют, в Low quality — отключаются).
- Игрок **не заполняет grid** и не считается блоком.

### 5.2 Character controller (hybrid locomotion, не raw physics)

| Параметр | Значение | Комментарий |
| --- | --- | --- |
| Acceleration | 3200 px/s² | отзывчивый разгон |
| Max run speed | 420 px/s (≈ 6.2 cells/s) | стакан 9 ячеек пересекается за ~1.3 s |
| Ground decel | 2600 px/s² | резкая остановка |
| Air control | ×0.55 | управление в воздухе сохраняется |
| Jump velocity | −940 px/s (высота ≈ 3.4 ячейки) | хватает перепрыгнуть 1–2 уложенных тела |
| Variable jump cut | ×0.5 при отпускании | короткие хопы для точных уклонений |
| Coyote time | 0.09 s | прощающий прыжок с края кучи |
| Jump buffer | 0.12 s | прыжок «чуть раньше приземления» |
| Dive speed | vy ≥ 1350 px/s | вход в stomp |
| Crouch | высота ×0.62, скорость ×0.55 | пролёт под падающим телом |

Контроллер применяет **импульсы/силы к Rapier-телу**, но скорость игрока clamp-ится и корректируется каждый шаг (никогда не «уносится» столкновением дальше 1.3 × max speed).

### 5.3 Stomp / утрамбовка

Два режима воздействия на кучу (см. §32):

| Режим | Условие | Радиус | Макс. Δv на тело | Макс. тел | Cooldown |
| --- | --- | --- | --- | --- | --- |
| Passive landing compress | любое приземление на кучу | 1.5 cell (102 px) | 90 px/s вниз+в стороны | 8 | — |
| Active dive stomp | dive + контакт с кучей | 2.2 cell (150 px) | 240 px/s (35% вниз-байас, остальное радиально) | 10 | 0.9 s |

Stomp — **управляемое** воздействие: каждое тело получает clamp-нутый импульс `Δv = dirFromImpact × falloff(d) × strength` с обязательным down-компонентом (закрывает микрогапы, проталкивает элементы вниз). Никаких импульсов больше caps. VFX: shockwave-ring, dust; SFX: глухой thump; score: +6 за смещённое тело (cap +30).

### 5.4 Игрок как объект стакана

- Игрока могут засыпать телами → **Trapped rule**: если центр torso игрока занят settled-телом непрерывно 4 s (struggle meter на экране) → game over «CRUSHED».
- Игрок может оказаться зажат между стеклянной стеной и кучей — та же trapped rule ловит и этот случай (нет движения + contact).
- Смертей от «HP» нет — урон через переполнение/погребение (§14), смыв очисткой ряда («Swept») и вырубание (stun) — см. ниже.
- **Смерть от очистки ряда («Swept»)**: если в момент resolve очистки игрок стоит на земле (grounded) и его torso-ячейка входит в очищенные ряды — его смывает вместе с рядом → game over «Смыло очисткой ряда». Контрплей: прыжок — в воздухе игрок спасён (warning-фазы 1.15 s телеграфируют опасность).
- **Вырубание (stun)**: если падающая часть (falling/landing) выше игрока, в пределах 44 px от головы и закрывается со скоростью > 210 px/с — управление выключается на 2.2 s: тело обмякает (вращение освобождено, случайное кувыркание), затем контроль возвращается (угол сброшен в 0).

## 6. Human Archetypes

### 6.1 Модули человечка

Каждый NPC состоит из трёх **core-модулей**, участвующих в grid-логике:

1. **Head** — сфера ~0.5 cell; footprint 1×1; доля массы ~13%.
2. **Torso** — капсула ~0.55 cell высотой, ~0.9 cell шириной; footprint 1×1 (straddling даёт 2 ячейки); доля массы ~47%.
3. **Legs / lower body** — pelvis-капсула + 2 leg-сегмента; grid footprint по pelvis 1×1; доля массы ~25%.

Плюс **ragdoll-скелет** (limbs, не участвуют в grid): armL, armR, legL, legR (упрощённая реализация; полные 8 сегментов — LOD0-опция контент-фазы, §7.4). Итого на NPC: **7 rigid bodies, 6 joints**.

Standing-человечек занимает **2 grid-ряда** (head в верхнем, torso+pelvis в нижнем). Стопка из двух человечков ≈ 3–4 ряда ≈ 204–272 px — как раз то, что перепрыгивает игрок.

### 6.2 Таблица архетипов

Стартовые tuning-значения (не догма). Размеры — в px при cell=68.

| Archetype | Scale | Mass | Размер (W×H) | Footprint | Restitution | Friction | Air drag × | Топpling bias | Роль в балансе | Unlock |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| NORMAL | 1.00 | 62 | 62×110 | 1 col | 0.06 | 0.85 | 1.00 | 1.0 | база; эталон веса и высоты | D1 |
| SMALL | 0.72 | 30 | 45×79 | 1 col | 0.08 | 0.9 | 1.15 | 1.2 | лёгкий кирпичик; легко утрамбовывается | D2 |
| TALL | 1.15 vert. | 70 | 64×150 | 1 col | 0.06 | 0.8 | 1.00 | 1.6 | высокий COM, падает набок, занимает 3 ряда | D3 |
| FAT | 1.10 horiz. | 110 | 108×115 | **2 col** | 0.04 | 0.95 | 1.05 | 0.6 | закрывает 2 колонки, почти непробиваем | D4 |
| LIGHT | 0.95 | 18 | 59×105 | 1 col | 0.10 | 0.7 | **1.7** | 2.0 | летит медленно, разлетается от stomp'ов | D2 |
| HEAVY | 1.05 | 130 | 65×116 | 1 col | 0.02 | 0.95 | **0.75** | 0.5 | падает быстро, якорь кучи | D3 |

`Toppling bias` — множитель случайного стартового углового момента при спавне (TALL/LIGHT заваливаются охотнее). `Air drag ×` — множитель линейного демпфера в воздухе (LIGHT падает медленно и читаемо, HEAVY — быстро и грозно).

### 6.3 Прогрессия типов

Ни один тип не доступен с первой секунды: веса архетипов зависят от уровня сложности D (§12). На D1 — только NORMAL; TALL/FAT/HEAVY появляются к D3–D4; к D7 пропорции смещаются к «плотной» смеси. Дизайн-цель: каждые ~40 секунд игрок встречает **новый тип проблем**, а не новый тип ради галочки.

### 6.4 Процедурная вариация (anti-clone)

Модульная 2D/2.5D-конструкция: каждый NPC собирается из вариантов слоёв при создании (и хранит вариант для detached pieces):

| Слой | Варианты | Диапазон |
| --- | --- | --- |
| Body proportions | head scale, shoulder width, hip width | ±8% вокруг archetype scale |
| Skin tones | 6 палитр | warm/neutral/deep |
| Hairstyles | 5 форм (cap, spikes, bun, bald, long) | + hair color 8 палитр |
| Shirts | 12 цветов, 3 паттерна (solid, stripe, duo-tone) | |
| Pants | 8 цветов | |
| Shoes | 4 цвета | |
| Facial features | глаза 3 формы, рот 4 формы, брови 3 | выражения: normal / worried / impact |
| Accessories | 0–1 (cap, glasses, headphones) | p ≈ 0.25 |
| Body scale | множитель archetype scale | ±6% |

Art style остаётся единым: все варианты рисуются в одной shape-language (см. §15), палитры ограничены общим color script. Вариация влияет только на визуал и ±6% scale — **не** на физику (иначе ломает баланс).

## 7. Ragdoll System

### 7.1 Скелет и joints

```text
        head (r=17, m≈8)
          │ neck joint [−40°, +40°]
        torso (capsule 30×20, m≈29)
        ┌───┴────────────┐
   shoulderL [−160°,+60°] shoulderR [−160°,+60°]
     armL (capsule 8×22, m≈3)      armR
        │
        │ spine joint [−30°, +40°]
        pelvis (capsule 26×16, m≈15)
        ┌───┴───┐
     legL (8×24, m≈3)   legR
```

- Все joints — **revolute** с angular limits: конечности болтаются свободно, но не выкручиваются на 360°.
- **Массы** нормализуются к archetype mass (доли: head 0.13, torso 0.47, pelvis 0.25, каждая limb 0.0375).
- Joints создаются через `world.createImpulseJoint(JointData.revolute(...), true)`; limits через `setLimits(min, max)`.
- Коллизии между joined-телами своего скелета отключены (Rapier исключает контакты соединённых тел), между чужими — включены.

### 7.2 Ragdoll state machine

Каждое **core-тело** человечка проходит состояния (limbs наследуют состояние своего скелета):

| Состояние | Условие входа | Поведение | Параметры |
| --- | --- | --- | --- |
| SPAWNING | активация из пула | тело disabled, стоит в spawn-точке | 1 кадр |
| FALLING | enabled, нет контактов | полная динамика, air drag архетипа | linDamp = 0.8 × dragArch |
| LANDING | первый существенный контакт (Δv > 300 px/s за шаг) | усиленное гашение энергии 0.4 s | доп. damp ×2.2, squash VFX, impact SFX |
| SETTLING | \|v\| < 160 px/s, есть контакт | нормальная симуляция | contact damping ×0.985/шаг при \|v\|<160 |
| SETTLED | \|v\| < 26 px/s && \|ω\| < 0.35 rad/s && контакт && 0.6 s непрерывно | `sleep()`, limb-коллайдеры disabled (LOD1), трансформы заморожены | коллайдер и occupancy сохраняются |
| WAKE_UP | импульс Δv > 140 px/s, Δω > 2.5 rad/s, разрушена опора (clear/stomp), контакт с awake-телом | limb-коллайдеры re-enabled, `wakeUp()` → SETTLING | без защитного окна |

**Ключевой принцип:** SETTLED-тело остаётся **реальным physics object** (rigid body + коллайдер + grid occupancy) — оно не превращается в декоративный спрайт. Заморожены только **limbs** (декоративные части) — это и есть LOD1 (§7.4). При wake-up всё возвращается.

### 7.3 Комичность без нестабильности

- Конечности болтаются, свисают, зацепляются за края куч — это revolute joints + limits + низкий angular damping в FALLING (1.5) и высокий в SETTLING (3.0).
- Перевороты — от честной физики (высокий COM у TALL, случайный стартовый момент), не от скриптов.
- Squash & stretch — **только визуально** (scale-пульс от impulse, cap 1.15/0.85, decay 6/s), физика не искажается.
- Ragdoll не «цепная реакция»: joints с лимитами + damping не позволяют конечностям раскрутить скелет.

### 7.4 LOD / simplification policy

| LOD | Когда | Скелет | Коллайдеры | Стоимость/NPC |
| --- | --- | --- | --- | --- |
| LOD0 | спавн → 1.5 s, или активное падение | 3 core + 4 limbs, 6 joints | все 7 | 7 bodies / 6 joints |
| LOD1 | SETTLING → SETTLED | 3 core активны, limbs **asleep + colliders disabled** | 3 core | 3 активных тела |
| LOD2 | куча глубже 6 рядов (нижние слои, похоронены) | core-тела спят, limbs заморожены | core спят | ~0 (только данные) |

Wake-up из LOD2 — только если соседний clear/stomp реально тревожит ячейки этого тела (grid-событие), иначе похороненные слои не просыпаются.

## 8. Physics Rules

### 8.1 Интеграция

- **Fixed timestep 60 Hz** (dt = 1/60 s) + **accumulator pattern**; физика никогда не привязана к FPS рендера.
- **Maximum substeps = 3** за кадр: если кадр длиннее 50 ms, симулируем 3 шага и **отбрасываем остаток** (игра замедляется, но не «взрывается» и не догоняет скачком).
- **Интерполяция рендера:** `alpha = accumulator / step`; визуал рисует тела между предыдущим и текущим transform'ом — никакого джиттера при 30/120 Hz мониторах.

### 8.2 Мировые константы (logical px, y вниз)

| Параметр | Значение | Зачем |
| --- | --- | --- |
| Gravity | 1800 px/s² (≈ 26.5 cells/s²) | читаемое падение: с верха стакана ~1.0 s |
| Max linear velocity | 2600 px/s (≈ 38 cells/s) | anti-explosion cap, clamp каждый шаг |
| Max angular velocity | 14 rad/s | anti-spin cap |
| Max single-impact Δv | 1200 px/s | любой контакт, добавивший телу больше, режется |
| Default linear damping | 0.8 (NPC в воздухе, × arch air drag) | |
| Default angular damping | 2.0 | |
| Contact linear damping | ×0.985/шаг при \|v\| < 160 px/s | быстрое успокоение кучи |
| CCD | включён для NPC и PIECE при \|v\| > 900 px/s | anti-tunneling |
| Стены/пол контейнера | static, толщина ≥ 32 px | anti-tunneling сквозь тонкие границы |
| Solver | Rapier impulse solver, warm starting on | |

### 8.3 Материалы (restitution / friction / density)

| Тело | Restitution | Friction | Плотность (kg/unit²) |
| --- | --- | --- | --- |
| Head | 0.10 | 0.6 | 1.0 (масса = доля archetype) |
| Torso | 0.05 | 0.85 | 1.0 |
| Pelvis (legs) | 0.04 | 0.9 | 1.0 |
| Arm / leg limbs | 0.08 / 0.05 | 0.5 / 0.7 | 1.0 |
| Detached piece | 0.05 | 0.85 | по роли |
| Floor | 0.00 | 0.9 | static |
| Glass walls | 0.05 | 0.2 | static |

Все материалы — data-driven (`src/config/physics.ts`), меняются без кода.

### 8.4 NO RANDOM LAUNCHING — список механизмов-ограничителей

После приземления запрещены взлёты, отпружинивания, улетания. Это обеспечивается **слоем политик поверх движка**:

1. Restitution ≤ 0.10 у всех человечьих тел (см. 8.3) — отскок физически ограничен.
2. Velocity clamp 2600 px/s и angular clamp 14 rad/s — пост-шаговая коррекция каждого тела.
3. Impact Δv cap 1200 px/s — редкий «плохой» контакт не может выстрелить телом.
4. Linear damping 0.8 + angular damping 2.0 — энергия гасится постоянно.
5. Contact damping ×0.985/шаг при малой скорости — куча «вязнет».
6. Sleeping policy (§8.5) — успокоенное тело выводится из симуляции.
7. Stomp/clear — только clamp-нутые импульсы (§5.3, §11), никаких взрывов.
8. Landing damping ×2.2 на 0.4 s после первого удара — тело «прилипает» к месту приземления.

### 8.5 How to prevent ragdoll explosions and tunneling in a crowded vertical container

**Причины взрывов:** (a) глубокие пенетрации в плотной куче → огромные корректирующие импульсы; (b) цепочка тел, толкающих друг друга; (c) конstraints+joints при высоких скоростях; (d) слишком много awake-тел на шаг.

**Причины tunneling:** тонкие коллайдеры + скорость > 1500 px/s + шаг 1/60.

**Митигции (все включены в baseline):**

| Механизм | Параметры |
| --- | --- |
| Velocity/angular caps | 2600 px/s / 14 rad/s, clamp каждый шаг |
| Impact Δv cap | 1200 px/s на одно событие |
| CCD | для NPC/PIECE при \|v\| > 900 px/s |
| Толстые границы контейнера | ≥ 32 px, static |
| Contact damping | ×0.985/шаг при \|v\| < 160 |
| Sleeping | порог §8.5 → sleep, wake только по событиям |
| Max substeps | 3 (кадр > 50 ms → drop remainder) |
| Spawn safety | минимальное разделение 0.6 cell, anti-overlap валидация (§45-логика в §33) |
| Penetration recovery | тела с пенетрацией > 0.5 cell после clear → wake + мягкий вытолкивающий подъем (только вверх, ≤ 60 px/s) |
| Cap населения | ≤ 34 core-единиц в стакане (StackManager) |

### 8.6 Sleeping policy + wake conditions

- **Порог сна:** \|v\| < 26 px/s && \|ω\| < 0.35 rad/s && есть контакт && 0.6 s непрерывно → `sleep()`.
- **При сне:** обнуляем скорости; коллайдер остаётся; grid occupancy остаётся; body остаётся в мире.
- **Wake:** (а) контакт с awake-телом (Rapier сам); (б) импульс/удар с Δv > 140 px/s или Δω > 2.5 rad/s; (в) разрушена опора (row clear/stomp убрал тело снизу); (г) anti-float watchdog: каждые 1.0 s спящее тело **без единого контакта** просыпается (страховка от «зависших в воздухе» тел после clear).
- **Wake-up не имеет защитного окна** — тело сразу SETTLING и подчиняется обычным caps.

## 9. Stack / Grid System

### 9.1 Стакан (logical layout, 720 × 1280)

```text
y=0 ─────────────────────────────
      HUD (плавает, прозрачный фон)      64 px
y=64 ─────  SPAWN ZONE ────────────    140 px (тела спавнятся на y≈150)
y=204 ───── GLASS TOP ──────────────
      GRID: 9 cols × 13 rows             884 px (612 px шириной, x: 54..666)
      ячейка 68×68; row 0 = дно
y=1088 ──── GLASS FLOOR ────────────   (игрок стоит на y=1088, внутри стакана)
y=1088..1280 ─ основание/пьедестал     192 px (декор)
```

- **Danger line:** y = 363 (82% высоты стакана) → ряды ≥ 10 — danger band. **Warning line:** ряд 8 (~68%) — мягкая индикация.
- Стакан низкий и видимый целиком: игрок всегда видит своего персонажа, ближайшие падающие тела, верх кучи и опасные ряды. Смерть «за экраном» невозможна по построению.

### 9.2 Hybrid model: physics layer vs grid layer

| | Physics layer (Rapier) | Grid layer (своя логика) |
| --- | --- | --- |
| Что это | rigid bodies, colliders, joints | Uint8-карта занятости 9×13 + реестр частей |
| Честность | полная (кривые позы, наклоны, пустоты) | нормализованные footprint-замеры |
| Кто кем управляет | grid **не двигает** тела | физика **не подгоняет** себя под сетку |

### 9.3 Grid occupancy algorithm (детально — псевдокод в §33.1)

**Input:** world transform части (x, y, angle), half-extents, archetype footprint, state.
**Output:** занятые ячейки с весами.

1. **Anchor:** каждая core-часть имеет grid-якорь — центр своего коллайдера (head/torso/pelvis; для pelvis — центр капсулы, leg-сегменты не замеряются).
2. **Oriented probes:** 5 probe-точек в локальных координатах части: центр (вес 1.0) + 4 угла на 0.55 × half-extents (вес 0.45). Пробы **вращаются вместе с телом** — наклонённое тело занимает горизонтальных соседей, а не большой AABB.
3. **Маппинг в ячейки:** каждая проба → ячейка (col, row) по мировым координатам; веса суммируются на ячейку.
4. **Порог с гистерезисом:** ячейка «занята» при весе ≥ **0.6**, освобождается при весе < **0.4** (нет мерцания на границе).
5. **Settleable filter:** вклад части зависит от состояния: FALLING → **0.0** (летящее тело не заполняет ряд), SETTLING → **0.5**, SETTLED/WAKE → **1.0**. Игрок → всегда 0.
6. **Сэмпл:** каждые 3 physics-шага (20 Гц); часть с \|v\| > 200 px/s и без контакта не сэмплится вовсе.
7. **Реестр:** для каждой части хранится список её ячеек (для resolve при clear), для каждой ячейки — список occupant'ов.

### 9.4 Row completion

- Row coverage = занятые ячейки / 9. **Строка заполнена при coverage ≥ 0.85 (8/9)** — допуск одной «дырки от ragdoll-мусора» (анти-фрустрация; tuning 0.85–1.0).
- Заполняют только core-части и detached pieces **в состояниях SETTLING (вес 0.5)/SETTLED (вес 1.0)**.
- Детекция — в фиксированном шаге, после world.step; событие ROW_COMPLETED уходит в transaction queue (§10.4, §22).

### 9.5 Grid properties

- Занятость — единственный источник правды для row clear; физика и grid могут временно расходиться (тело летит) — это нормально, grid ждёт стабилизации.
- Grid не знает о визуале; рендер читает физику напрямую.
- После каждого clear grid **пересчитывается с нуля** (полный ресэмпл) — дешёво (~30 частей × 5 проб).

## 10. Row Clearing

### 10.1 Пять фаз (тайминги — tuning-значения)

| Фаза | Длительность | Что происходит |
| --- | --- | --- |
| **1. COMPLETE** | 0 | grid фиксирует coverage ≥ 0.85 → событие ROW_COMPLETED в очередь |
| **2. WARNING** | 0.45 s | строка подсвечивается жёлтым пульсом; звуковой cue; HUD-чип; музыка +1 интенсивность |
| **3. DANGEROUS** | 0.70 s | сильный красный флеш; игрок может перепрыгнуть, уйти, stomp-ить; tension-звук |
| **4. CLEAR** | 0.15 s | resolve + apply транзакции: уничтожение модулей в строке, detach сирот; визуальный slice + частицы + hit-stop 60 ms |
| **5. RECOMPOSITION** | 0.15 s | полный ресэмпл grid; проверка цепочки: новые заполненные строки → сразу COMPLETE (multi-row) |

Суммарно от COMPLETE до APPLY: **1.30 s** — достаточно, чтобы отреагировать, но давление растёт.

### 10.2 Правила уничтожения модулей

- **Full-in-row:** все занятые ячейки части ∈ строке → уничтожается целиком.
- **Slice (torso/pelvis only):** часть straddling границу (заняла ячейки в 2 строках) уничтожается, если строка покрывает **≥ 50%** её ячеек; выжившие части соседей.detach'атся.
- **Head (1×1):** без slice — либо ячейка в строке (destroy), либо нет (survive). **Edge threshold:** если голова опрокинута и её ячейка попала в строку, но центр головы выше границы строки более чем на 0.5 cell → голова **не** в строке (выживает, остаётся лежать на куче).
- **Partial < 50%:** часть выживает, её ячейки в строке освобождаются (occupancy обновится ресэмплом).

### 10.3 Re-validation

В момент RESOLVE (начало фазы 4) grid **пере-замеряет** строку по живым данным: если coverage упал < 0.85 (куча съехала) → clear **отменяется**, подсветка гаснет, начисляется небольшой dodge-бонус игроку, если он был рядом. Строка может завершиться снова позже.

### 10.4 Transaction pipeline (критично — см. §22, §33.2)

```text
ROW_COMPLETED → ClearScheduler (WARNING → DANGEROUS)
→ RESOLVE: пере-замер → список мутаций [DESTROY_PART, DETACH_JOINT, FREE_CELL]
→ APPLY: мутации применяются ТОЛЬКО на границе фиксированных шагов,
  вне коллбеков физики; затем wake затронутых тел → полный ресэмпл occupancy
```

Никакие изменения физического мира не выполняются внутри `world.step`/коллбеков — только через очередь на безопасной границе шага.

### 10.5 Multi-row

Если строки R и R+1 завершились в одном сэмпле → **одна транзакция**, оба clear'а вместе: один VFX-sweep, бонус +180 за каждую дополнительную строку, combo растёт на 2.

### 10.6 Edge cases (обязательные)

| Case | Ситуация | Правило |
| --- | --- | --- |
| **A** | Все 3 core-части в строке | все 3 уничтожены, human удалён из реестра |
| **B** | Только torso в строке | torso уничтожен; head и legs (pelvis+limbs) **detach** → независимые pieces |
| **C** | Head пересекает строку только краем | порог: центр ниже границы строки − 0.5 cell → в строке; иначе выживает |
| **D** | Несколько людей в одной строке | уничтожаются только их модули в строке; остальныt части живут |
| **E** | Detached piece сам попал в строку | считается обычным grid-блоком и уничтожается (с очками) |
| **F** | Clear во время активного столкновения | транзакция: мутации на границе шага; тела с пенетрацией → мягкий recovery-подъём ≤ 60 px/s (§8.5) |
| **G** | Несколько строк одновременно | одна транзакция, порядок снизу вверх, единый VFX, multi-row бонус |

## 11. Detachment System

### 11.1 Structural split

```
HEAD → BODY → LEGS
если BODY destroyed:  HEAD → independent piece
                      LEGS → independent piece (pelvis + 2 leg-сегмента остаются под-скелетом)
если HEAD destroyed:  BODY+LEGS остаются соединёнными (одна структура, role=TORSO+LEGS)
если LEGS destroyed:  HEAD+BODY остаются соединёнными
```

Разрываются **только joints к уничтоженной части**. Внутренние связи выживших (например, pelvis↔legs) сохраняются — «половина человечка» продолжает жить как цельная структура.

### 11.2 Что сохраняют detached pieces

| Свойство | Правило |
| --- | --- |
| Позиция / ориентация | сохраняются точно (без телепортов) |
| Velocity | сохраняется, **clamp** ≤ 260 px/s линейно, ≤ 3 rad/s углов |
| Импульсы при detach | **никаких** (§8.4 п.7, §44) — тело просто теряет опору и честно падает |
| Sub-skeleton | внутренние joints выживших частей сохраняются |
| Identity | вариант внешности наследуется (голова остаётся «той самой головой») |
| Grid footprint | своя роль: HEAD 1×1, TORSO 1×1, LEGS 1×1 (по якорю) |
| Sleeping | просыпаются при detach (потеря опоры), засыпают по общим правилам |

### 11.3 Pieces = новые блоки

Каждый detached piece — полноценный stackable объект с собственными mass, collider, dimensions, footprint, материалом, sleeping state. Он **продолжает заполнять будущие строки** наравне с целыми человечками. Row clear не удаляет всё выше/ниже строки — только то, что действительно в ней.

### 11.4 Порядок операций при detach

```text
1. resolveRowClear() → { destroyed[], orphanedHumans[], freedCells[] }   (чистая функция, тестируется)
2. для каждого orphaned human: разорвать joints к уничтоженной части
3. выжившим частям: clamp velocity → wakeUp()
4. уничтоженные части: снять с физики, в пул, VFX (slice-flash, cloth-частицы, pop)
5. wake тел, опиравшихся на уничтоженные (снизу освобождено — падают сверху... т.е. тела ВЫШЕ
   очищенных ячеек просыпаются и честно оседают)
6. полный ресэмпл occupancy
```

### 11.5 Edge cases

- **Detached head в строке** — обычный блок (Case E), уничтожается, очки как за row-блок.
- **Orphan с одной выжившей частью** — та становится piece (никаких «одиночных пустых человечков»).
- **Огромный каскад**: транзакция обрабатывает все строки/людей за один APPLY — промежуточных состояний нет.
- **Clear под игроком**: игрок просто падает честно (опора исчезла); +60 «risky clear», если он был в границах строки при APPLY и выжил.

## 12. Difficulty

### 12.1 Формулы (data-driven, `src/config/difficulty.ts`)

```text
t = время выживания, s
D(t) = min(7, 1 + floor(t / 40))                      // уровень сложности 1..7
spawnInterval(D) = max(0.8, 2.7 − 0.30 × (D − 1))     // D1: 2.7s … D7: 0.9s
spawnVelocity(D) = 150 + 30 × (D − 1) px/s            // стартовая скорость падения
targetPlayerP(D) = min(0.50, 0.12 + 0.07 × (D − 1))   // вероятность спавна "на игрока" (±1 cell)
```

### 12.2 Веса архетипов по уровням

| D | NORMAL | SMALL | LIGHT | TALL | HEAVY | FAT | Характер |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 100 | — | — | — | — | — | «тёплый старт», только база |
| 2 | 78 | 14 | 8 | — | — | — | первые вариации массы |
| 3 | 62 | 16 | 10 | 8 | 4 | — | первый «вертикальный» риск |
| 4 | 50 | 14 | 10 | 12 | 8 | 6 | первые 2-колоночные тела |
| 5 | 40 | 12 | 10 | 14 | 12 | 12 | плотная куча |
| 6 | 34 | 10 | 10 | 14 | 14 | 18 | давление |
| 7 | 28 | 8 | 12 | 16 | 16 | 20 | финальная плотность |

### 12.3 Принципы

- Плавность: между уровнями нет скачков — веса интерполируются линейно внутри уровня (lerp к следующему).
- Никогда не «стена смерти»: сложность растёт медленнее, чем растёт умение игрока на первых 2–3 минутах.
- Spawn Director — единственный источник «злости» (см. §27-логику в GDD §33.3): targeting, интервалы, анти-фрустрация.

### 12.4 Anti-frustration (встроен в Spawn Director)

- Коридор спавна должен иметь клиренс ≥ 1.2 × ширины тела; иначе выбирается другой x (до 6 попыток, затем центр стакана).
- При D < 4 не бывает двух спавнов в одну колонку с интервалом < 0.4 s.
- Если последние 5 спавнов были не-NORMAL — следующий гарантированно NORMAL («передышка»).
- Прямо над игроком (та же колонка ±0.5 cell) спавн запрещён, если игрок стоит под почти заполненным рядом (danger-фаза).
- Grace period game over — 2.5 s (§14).

| Multi-row (доп. строка в транзакции) | +180 / строка | |
| Combo | ×(1 + 0.35 × (combo − 1)), cap ×4 | комбо растёт за каждый clear, декей 5 s без событий |
| Dodge (near miss) | +20 | падающее тело прошло в 1.1 cell от центра игрока без касания при \|vx игрока\| > 120 |
| Stomp | +6 / смещённое тело, cap +30 / stomp | |
| Risky clear | +60 | игрок был в границах строки при APPLY и выжил |
| Physics moment | +15 | редкие: тело приземлилось на голову другому (stack tower), 2+ тела в одной ячейке-цепочке |

### 13.2 Combo

```text
combo += 1 на каждый clear-транзакцию (multi-row = +2)
comboTimer = 5.0 s; истёк → combo = 0
multiplier = 1 + 0.35 × max(0, combo − 1), cap ×4
```

### 13.3 Принцип

Score вознаграждает **skillful play**: пассивное выживание даёт ~12/s, активная игра (clears + dodges + stomps) — в 4–8 раз больше. Best score сохраняется (§51), прогрессия косметики — по порогам best score (§62).

## 14. Game Over

### 14.1 Условия (все — с grace period)

| Условие | Проверка | Grace |
| --- | --- | --- |
| **Stack overflow** | coverage danger band (ряды ≥ 10) > 0 непрерывно 2.5 s | во время grace — пульсирующий danger-UI, игрок может stomp'ом/прыжком сбить кучу ниже линии |
| **Trapped** | центр torso игрока занят settled-телом (или нет движения при контакте) непрерывно 4 s | struggle meter растёт, «рывок» stomp-ом спасает |
| **Spawn blocked** | нет валидного коридора спавна 6 s подряд | практически недостижимо, страховка |
| **Swept** | игрок grounded и его torso-ячейка входит в очищенные ряды в момент resolve очистки | warning-фазы 1.15 s телеграфируют: прыжок спасает (в воздухе игрок не смывается) |

### 14.2 Sequence

```text
условие → hit-stop 120 ms → slow-mo ×0.3 (0.6 s) → fade → GAME OVER экран
(score, best, новый best badge, причина смерти человеческим текстом, Retry / Menu)
```

- **Причина смерти** всегда текстом и по-человечески: «Стакан переполнился», «Тебя засыпало», «Некуда падать», «Смыло очисткой ряда» — P3 (readable chaos).
- Retry — мгновенный (мир пересоздаётся < 200 ms), seed по умолчанию случайный; `?seed=` фиксирует.

## 15. Visual Direction

### 15.1 Стиль

**Premium stylized physics toy**: «дорогая» 2D с ощущением 2.5D. Не реализм, не blood/gore, не creepy anatomy. Ориентир настроения — premium mobile physics game + polished web game + modern cartoon animation (не копируем конкретные игры).

### 15.2 Shape language и материалы

- **Expressive cartoon humans:** читаемые силуэты, мягкие скруглённые формы, крупные головы (~40% высоты), простые лица.
- **7 выражений лиц (FACE FSM):** normal (стоит) / terror (летит — рот открыт в ужасе) / concussion (ударился — контузия ~1.6 s после сильного удара) / ko (лежит — глаза закрыты) / scream (лежит и двигается — орёт) / dead (голова отсоединилась — 2 крестика + высунутый язык) / run (бежит). У игрока: normal/run/jump/ko (вырубился)/dead. Глаза и рты — явные полилинии (moveTo/lineTo), без engine-arc.
- **Мягкие материалы:** 2-тонная заливка (base + shade) на каждой части, тёплый ambient, холодный rim light.
- **Soft shadows:** эллипс-тень на полу для игрока и летящих тел (alpha от высоты), мягкая ambient occlusion — градиент внизу стакана.
- **Depth layering:** bg (градиент + мягкие формы интерьера) → glass walls (полупрозрачные, rim) → pile/humans → player → VFX → foreground vignette. Стек/куча имеют максимальный visual priority.

### 15.3 Motion rules

- Squash/stretch — только визуально, от impulse, cap 1.15/0.85, decay 6/s.
- Камера: micro-shake по trauma-системе (shake = trauma², add 0.15 × impulse/1000, decay 1.2/s, cap 1.0), zoom-пульс 1.012 на 0.2 s при clear. **Постоянного shake нет.**
- Партиклы: dust при ударе, cloth-конфетти при destroy, sparkles при clear, pop-rings при detach. Пул 600, cap 350 живых.

### 15.4 Стакан и среда

Вариант baseline: **laboratory glass tube / toy machine**: две стеклянные стенки с rim-светом, металлический пьедестал, мягкий внутренний shadow, faint row guides (alpha 0.05), danger line — красный пунктир, warning — жёлтый пульс. Фон: приглушённая лаборатория (виньетка, пара мягких силуэтов), не отвлекает.

## 18. Technical Stack Comparison

По протоколу **Requirement → Options → Pros/Cons → Performance → Complexity → Recommendation** (§73).

### 18.1 Requirements (из требований именно этой игры)

1. Ragdoll joints с angular limits, сотни тел в вертикальном контейнере.
2. Стабильность: sleeping, velocity caps, collision groups, CCD, deterministic sim для тестов.
3. Renderer: спрайтовые batch'и, texture atlas, particles, depth layers, WebGL fallback.
4. Mobile performance (thermal, 30 FPS floor без поломки симуляции).
5. Developer experience: TypeScript-first, Vite, отладка физики.
6. Собственный игровой цикл (physics ≠ presentation) — framework opinionation вреден.

### 18.2 Option A — PixiJS + Rapier 2D (impulse-based, Rust→WASM)

| Критерий | Оценка | Комментарий |
| --- | --- | --- |
| Ragdoll joints | **отлично** | revolute/prismatic/fixed/spring + **angular limits нативно** + motors |
| Physics stability | **отлично** | impulse solver, warm starting, CCD, sleeping, deterministic (Rust, фикс. точность) |
| Sleeping / много тел | **отлично** | Rapier sleeping из коробки, broad-phase, ~100+ тел без деградации |
| Collision handling | отлично | interaction groups (16+16 бит), collision events, contact force events |
| Bundle size | хорошо | rapier2d-compat ≈ 2 MB (WASM base64), pixi ≈ 450 KB gzip |
| DX / TS | отлично | первоклассные TS-типы, Vite-friendly, `RAPIER.init()` без fetch |
| Debugging | хорошо | свои debug-обёртки + визуальные dump'ы transform'ов |
| Maintainability | отлично | физика изолирована за своим слоем; движок не диктует архитектуру |

**Cons:** WASM-инициализация асинхронна (решается boot-этапом); нет per-pair filter callback в JS API (обходится interaction groups); ~2 MB к бандлу.

### 18.3 Option B — Phaser 4 + Matter.js

| Критерий | Оценка | Комментарий |
| --- | --- | --- |
| Ragdoll joints | средне | constraints есть, **angular limits — хак через angle constraints**; нет настоящих motors |
| Physics stability | слабо-средне | Matter sequential solver, известные проблемы со stacking 100+ тел, tunneling на быстрых телах |
| Sleeping | средне | есть, но слабее и хуже контролируется |
| Bundle | средне | phaser ≈ 1 MB, matter ≈ 80 KB |
| DX | средне | полноценный фреймворк навязывает scene/loop — конфликтует с «physics ≠ presentation» |
| Maintainability | средне | Matter в режиме поддержки; кастомизация солвера ограничена |

**Cons:** главные — стабильность кучи из сотен тел и limits для ragdoll'ов; фреймворк-опионированность.

### 18.4 Option C — прочие (Planck.js / custom)

- **Planck.js** (Box2D порт): стабильный солвер и limits, но API C-стиля, тяжелее DX, нет узкого TS-типирования, тело-сообщество меньше. Достойный fallback, но Rapier покрывает то же + детерминизм + WASM-скорость.
- **Custom engine:** полный контроль над «no random launching», но рукописный box-box SAT + sequential impulses + joints + limits + sleeping — это ~1500 строк критичного кода с высоким риском численных багов; не нужно, когда Rapier существует.

### 18.5 Recommendation

> **Option A: TypeScript + Vite + PixiJS v8 + Rapier 2D (compat).**

Решающие аргументы: (1) единственный из кандидатов с **нативными angular limits + deterministic solver + надёжным sleeping** — ровно три столпа этой игры; (2) физика изолирована за своим слоем, PixiJS — чистый рендер без opinionation; (3) WASM-скорость для сотен тел; (4) TS-first. Phaser+Matter проигрывает по стабильности кучи — ключевому риску проекта.

## 19. Final Architecture Decision

```text
TypeScript (strict) · Vite 6 · PixiJS v8 (WebGL2; WebGPU — progressive enhancement)
Rapier 2D compat (WASM) · Web Audio API (процедурный звук) · Playwright (E2E)
```

- **Рендерер:** PixiJS v8, `preference: 'webgl'` по умолчанию; `?gpu=1` / настройка Quality→High пытается WebGPU, при неудаче — автоматический fallback на WebGL (try/catch на `app.init`). WebGL fallback для production — надёжный путь.
- **WASM:** `@dimforge/rapier2d-compat` — WASM зашит base64, `await RAPIER.init()` без отдельного ассета и без CORS-сложностей.
- **Аудио:** процедурный (osc + noise + biquad) — ноль аудио-ассетов в baseline; data-driven паттерны позволяют подменить файлами в контент-фазе.
- **UI:** DOM-оверлей (не React) — тонкий, обновляется ≤ 10 Гц.
- **Тесты:** Vitest (unit + physics-интеграция в Node — rapier-compat работает в Node) + Playwright smoke.

**Почему не Phaser:** см. 18.3. **Почему не чистый Canvas2D:** sprite-batching и atlas'ы дают ×5–10 на куче спрайтов; PixiJS v8 даёт и WebGPU-путь.

## 20. Code Architecture

### 20.1 Слои и правила зависимостей

```text
UI (DOM) ─┐
Audio ────┤
Render ───┤──► Gameplay ──► Physics (Rapier за обёрткой) ──► config (data)
          │        │
          │        └──► core (Clock/Events/Rng) ◄── Infrastructure (Pool/Save/Perf/Debug)
```

- **Запрещено:** Gameplay не импортирует PixiJS; Render не импортирует Rapier; Physics не знает о gameplay-понятиях (row, score).
- **Разрешено:** Gameplay читает физику через свои типы (`PhysBody`, `PhysicsWorld`); Render читает transform'ы физики напрямую (physics → pose → render).
- Чистые модули (GridManager, RowDetector, DetachmentResolver, ScoreSystem, DifficultyDirector, ClearScheduler-логика) — **без импортов движков**, полностью тестируемы.

### 20.2 Модули

| Слой | Модули |
| --- | --- |
| **Core** | `Game` (оркестратор + state machine MENU/PLAYING/PAUSED/GAMEOVER), `Clock` (rAF, accumulator, substeps, alpha), `Events` (типизированная очередь транзакций), `Rng` (mulberry32, seed) |
| **Physics** | `PhysicsWorld` (обёртка Rapier: step, bodies, joints, events, queries), `RagdollFactory`, `PieceFactory`, `materials` |
| **Gameplay** | `PlayerController`, `HumanSpawner`, `RagdollSystem` (FSM, damping, sleep, LOD), `GridManager`, `RowDetector`, `ClearScheduler`, `DetachmentSystem`, `StackManager` (danger band, trapped, caps), `ScoreSystem`, `DifficultyDirector` |
| **Rendering** | `Renderer` (Pixi app, letterbox, dpr), `CameraSystem` (trauma shake), `EnvironmentRenderer`, `HumanRenderer`, `PlayerRenderer`, `VfxSystem`, `AtlasFactory` (процедурные текстуры) |
| **UI** | `Ui` (роутер экранов), `Hud`, `Menus`, `Settings`, `TouchControls`, `DebugOverlay` |
| **Audio** | `AudioManager`, `SfxSynth`, `MusicDirector` |
| **Infrastructure** | `ObjectPool`, `Save`, `PerformanceMonitor`, `DebugSystem` |

### 20.3 Потоки данных

```text
Input → PlayerController → (impulses) → PhysicsWorld.step
Spawn Director → (activate body) → PhysicsWorld
PhysicsWorld.step → collision events → RagdollSystem (FSM)
RagdollSystem → (transforms) → GridManager.sampling → RowDetector → ClearScheduler (queue)
ClearScheduler → DetachmentSystem → (destroy/detach/wake) → PhysicsWorld [граница шага]
ScoreSystem ← события ← ClearScheduler/PlayerController/DetachmentSystem
Render ← transforms ← PhysicsWorld (интерполяция); UI ← HUD-снимок ≤ 10 Гц
```

## 22. Update Loop

### 22.1 Порядок в фиксированном шаге (60 Гц) — точный

```text
FIXED STEP (dt = 1/60):
 1. ClearScheduler.tick(dt)          — таймеры фаз warning/dangerous; due-транзакции помечаются APPLY
 2. ApplyPendingMutations()          — destroy/detach/joint-reconfig/wake НА ГРАНИЦЕ ШАГА (§68)
 3. PlayerController.update(dt)      — input → импульсы/силы; coyote/buffer; clamp скорости игрока
 4. HumanSpawner.update(dt)          — таймер спавна; corridor check; activate body
 5. PhysicsWorld.step()              — один фиксированный шаг Rapier; события только в очередь
 6. DrainCollisionEvents()           — contact-реестр (трогающие тела), impact-метрики (Δv)
 7. RagdollSystem.update(dt)         — FSM частей (falling→landing→settling→settled), contact damping,
                                       sleep/wake, LOD (limb freeze), velocity caps (anti-explosion)
 8. GridManager.sample()             — каждые 3 шага: probes → occupancy → гистерезис
 9. RowDetector.detect()             — coverage ≥ 0.85 → ROW_COMPLETED в очередь ClearScheduler
10. StackManager.update(dt)          — danger-band grace, trapped, population caps
11. ScoreSystem.update(dt)           — выживание, декей комбо
12. DifficultyDirector.update(t)     — уровень, параметры спавна
```

### 22.2 Порядок в render-кадре

```text
RENDER FRAME (rAF):
 1. Clock.accumulate(dtMs)           — аккумулятор; до 3 фиксированных шагов; излишек отбрасывается
 2. alpha = acc / step
 3. CameraSystem.update(dtMs)        — trauma decay, zoom pulse; применение к worldRoot
 4. Renderer.render(alpha)           — интерполяция transform'ов: prev + (curr − prev) × alpha
                                        env → humans → player → vfx → debug draw
 5. VfxSystem.update(dtMs)           — партиклы, floating text (dt-основанные)
 6. Hud.update()                     — ≤ 10 Гц, DOM-тексты
 7. PerformanceMonitor.tick(dtMs)    — rolling avg, auto-quality
 8. DebugOverlay.update()            — если включён
```

### 22.3 Что где живёт

| Fixed step (детерминированно) | Render frame (недетерминированно) |
| --- | --- |
| вся физика, FSM, grid, rows, clear/detach, score, difficulty, спавн | интерполяция, камера, VFX, HUD, аудио-параметры, авто-качество |

Игровые таймеры (warning/danger/grace/trapped) — **в фиксированном шаге** (детерминизм для тестов). VFX/камера — в кадре (гладкость).

### 23.3 Откуда берётся экономия

- **Sleeping policy:** большинство тел в куче спят (не стоят ничего в солвере).
- **LOD1:** limb-коллайдеры отключаются у settled-человеков (7 → 3 коллайдера).
- **Пул:** ни один human/particle/floating text не создаётся в бою заново.
- **Atlas + тинты:** все части из 2–4 текстур, батчатся; цвета — tint'ами.
- **Grid-сэмпл 20 Гц**, а не 60; DOM HUD 10 Гц.

### 23.4 Auto-quality degradation (§55)

`PerformanceMonitor`: avg frame > 24 ms на протяжении 4 s → tier −1; avg < 15 ms на протяжении 10 s → tier +1 (не выше выбранного). Tier влияет: dpr (2 → 1.5 → 1), particles ×(1 / 0.7 / 0.4), shadows off, limb-LOD агрессивнее, фоновая анимация off, limb-player коллизии off (Low). **Основная gameplay-физика никогда не деградирует** — фиксированный шаг сохраняется всегда.

## 31. Acceptance Criteria

### 31.1 Gameplay (measurable)

1. Игрок стабильно перемещается и прыгает; coyote/buffer работают (ручной QA + E2E).
2. **20+ тел одновременно** в стакане — ноль physics explosions (autotest seed_008 + ручной прогон).
3. Тела после landing успокаиваются: ≥ 90% settled за ≤ 4 s (autotest).
4. Row clear не создаёт взрывных импульсов: max post-clear Δv ≤ 260 px/s (autotest).
5. Detached pieces остаются в игре и заполняют будущие строки (autotest seed_003/007).
6. Grid корректно детектит строки на всех 9 seed-сценариях (unit + physics tests).
7. Partial humans split correctly: head/legs выживают, torso уничтожается (seed_003).
8. Игра играбельна после 10+ подряд clear (ручной QA gate).
9. Ноль unrecoverable stack bugs на 10 полных сессиях (ручной QA).
10. Ноль frame pacing катастроф: p95 frame ≤ 20 ms desktop (PerformanceMonitor).

## 33. Pseudocode

### 33.1 Grid occupancy sampling

```text
function sampleOccupancy():
  clearTransientWeights()
  for part in parts where part.state in {SETTLING, SETTLED} and part.alive:
    stateWeight = part.state == SETTLING ? 0.5 : 1.0
    probes = [(0,0,1.0)] + [(±0.55*halfW, ±0.55*halfH, 0.45) × 4]
    for (lx, ly, w) in probes:
      wx = part.x + lx*cos(part.angle) − ly*sin(part.angle)
      wy = part.y + lx*sin(part.angle) + ly*cos(part.angle)
      (col, row) = cellAt(wx, wy)             // границы стакана; вне — skip
      transient[col][row] += w × stateWeight
  for each cell:
    if transient ≥ 0.6: occupied ← true        // enter
    else if transient < 0.4: occupied ← false  // exit (гистерезис)
    обновить cell.occupants ← часть(cell, part)
  rebuildPartCellLists()
```

### 33.2 Row clear transaction

```text
on ROW_COMPLETED(row) → queue.push({type: ROW_COMPLETED, row})

ClearScheduler.tick(dt):
  for job in queue:
    phase WARNING: glow row; t += dt; t ≥ 0.45 → DANGEROUS (sfx tension)
    phase DANGEROUS: strong flash; t += dt; t ≥ 0.70 → RESOLVE
    phase RESOLVE:
      coverage = revalidateCoverage(row)          // по живым данным
      if coverage < 0.85 → CANCEL (fade glow; optional dodge bonus)
      else → buildMutations(row):
        partsInRow = parts с ячейками ∈ row
        for part in partsInRow:
          if all cells of part ∈ row → DESTROY_PART(part)
          elif role ≠ head and cellsInRow ≥ 0.5 × cells → DESTROY_PART(part)  // slice
          else → FREE_CELL(part, row)                                          // выживает
        orphanedHumans = humans с (destroyed part ∧ alive parts)
        → APPLY
    phase APPLY:                                    // на границе шага:
      for part in destroyed: physics.destroyPart(part) (→ пул, VFX)
      for human in orphanedHumans: physics.cutJointsTo(human, destroyedRoles);
        for survivor: clampVelocity(≤260 px/s, ≤3 rad/s); wakeUp()
      for body над очищенными ячейками: wakeUp()    // честное падение
      fullResampleOccupancy()
      score.onClear(row, multiRowCount)
      → RECOMPOSE → chain check → новые ROW_COMPLETED

on DESTROY_PART → never внутри physics callbacks; только queue → APPLY
```

### 33.3 Spawn safety

```text
function trySpawn(archetype):
  for attempt in 1..6:
    x = pickSpawnX(archetype, attempt)            // anti-frustration: не над игроком в danger
    corridor = {x ± 0.6×width, y: spawnY..spawnY+height}
    if corridorFree(corridor):                    // min separation 0.6 cell до ближайших тел
      activateRagdoll(archetype, x, spawnY)       // из пула, полная вариация
      return true
  lastResort: центр стакана
  return false
```

### 33.4 Ragdoll FSM (на core-часть)

```text
FALLING:  if contact && Δv > 300 → LANDING (landTimer 0.4)
LANDING:  доп. damping ×2.2; t −= dt; t ≤ 0 → SETTLING
SETTLING: contact damping; if |v|<26 && |ω|<0.35 && contact: settleTimer += dt
          else settleTimer = 0
          settleTimer ≥ 0.6 → SETTLED: sleep(); freezeLimbs(true)
SETTLED:  (тело спит; проверяется только на wake-события)
onWake(dv, dω, supportLost): freezeLimbs(false); wakeUp(); → SETTLING
```

### 33.5 Player stomp

```text
onLanding(impactPoint, wasDiving):
  strength = wasDiving ? 240 : 90; radius = wasDiving ? 150 : 102
  for body in bodiesInRadius(impactPoint, radius):     // ≤ 10 тел
    d = dist(impactPoint, body.pos); falloff = 1 − d/radius
    dv = falloff × strength
    dir = normalize(body.pos − impactPoint) × 0.65 + down × 0.35
    impulse = dir × dv × mass(body)                    // clamp per-body
    applyImpulse(body, impulse)
    score.stompHit(); vfx.dust(impactPoint); audio.thump()
```

### 33.6 Fixed timestep loop

```text
frame(dtMs):
  if playing: acc += min(dtMs, 250)
  steps = 0
  while acc ≥ step && steps < 3: fixedStep(step); acc −= step; steps++
  if acc ≥ step: acc = 0          // излишек отброшен (честное замедление)
  alpha = acc / step
  render(alpha)
```

## Appendix B. Project Philosophy

1. **“You don't control the falling humans. You control the human who survives underneath them.”** — весь дизайн влияния игрока на мир — через движение, прыжок и stomp. Никаких катапульт.
2. **“Physics creates the situation. The grid gives the situation rules.”** — физика честная и кривая; сетка только замеряет и вердиктует, никогда не двигает тела.
3. **“The chaos should come from bodies interacting, not from random impulses.”** — никакой пинбол-физики; вся динамика — от массы, трения и лимитов.
4. **“Every cleared row should create a new interesting physical situation.”** — detachment делает каждый clear новой головоломкой: pieces, пустоты, новые stomp-возможности.

**И главное — прототип уже fun до добавления контента:** одна механика (выживание + row clear + detach), 6 архетипов, сочный feedback — и игра готова к vertical-slice тесту на реальных игроках.
